**atrum.fun**

**Revision of `atrum-build-plan.md`, scoped to a 4-day delivery window.** The original plan is an 8-week plan and remains the north star — nothing here contradicts it, this file only decides *which parts ship first* and *what the site is allowed to claim* as a result.

The scope cut taken here is **cut line #3, exactly as the original plan wrote it**:

We are taking that cut deliberately and up front, not discovering it on day 3. Everything else in the original plan's cut-line order is preserved, including the one that is never cut.

## 0. What ships in 4 days, one paragraph

**Several** single-event prediction markets ("Will X happen?" — one question each, YES/NO, no conditional nesting), all drawing on **one shared shielded pool**, where **who bet, and what any individual bet, is hidden from everyone including the operator** — enforced by ZK proofs, not by a company's promise — while **pool totals and odds are public**, the same as every prediction market shipping today. Bets are fixed-denomination. Redemption is private, inside the shielded pool, never as a public claim. Resolution is a disclosed multisig (R5), with an immutable resolution spec committed at market creation.

"Single-event" means each market is one plain YES/NO question — the opposite of a *conditional* market ("if A happens, will B?"), which is a genuine architectural jump the original plan deliberately excluded. It does **not** mean one market on the platform; §3.1 is explicit that many markets share one anonymity set, and the original plan is blunt that *"breadth is the thesis, one market proves nothing."*

What this is: an anonymous-participant parimutuel market with private settlement. What it is not: encrypted pool totals (§4), and not a trustless resolver (§5).

## 2. [CORRECTION] The MACI claim in the original plan is overstated

The original plan and `nisi-master-reference.md` §C2 both say MACI is *"a production ElGamal-on-BabyJubJub voting system using the same stack — proven combination"* and name it *"the reference implementation to read"* for the Phase 2 accumulator.

Checked. That is not accurate in the way it matters:

- Production MACI encrypts commands with an **ECDH shared key + Poseidon** (symmetric), decrypts off-chain, and proves the tally was computed correctly with a SNARK. It does **not** perform homomorphic ElGamal addition on-chain. [DOCUMENTED, maci.pse.dev]
- ElGamal in MACI exists only on an **unmerged experimental branch** (`feat/elgamal`), and its purpose there is re-randomisation to hide *which voter acted* — not summing encrypted amounts. Different problem. [DOCUMENTED, github.com/privacy-ethereum/maci/tree/feat/elgamal]
- `circomlib` ships BabyJubJub point arithmetic and Poseidon — the ingredients — but **no ElGamal encrypt-and-prove circuit**. The only ready implementation found is a single unaudited independent repo. [DOCUMENTED, github.com/iden3/circomlib]

**What this changes.** The C2 mathematics is textbook and the 1,715 gas figure for the on-chain add stands. But Phase 2 is **novel circuit work with no audited prior art to adapt**, not an integration job. Cryptographic bugs there fail silently rather than at compile time. This makes the decision to defer Phase 2 out of a 4-day window a correctness call, not just a scheduling one.

This correction should be carried back into `atrum-build-plan.md` §5 and `nisi-master-reference.md` §C2 when the 8-week track resumes.

## 3. Scope

| In, shipping in 4 days | Out, deferred to the 8-week plan |
|---|---|
| Vault: fixed-denomination deposit into **one shared** shielded pool | ElGamal accumulator (C2) |
| **`marketId` bound into every position note** — many markets, one anonymity set | Threshold committee, t-of-n |
| `bet` circuit: spend note → `(marketId, outcome)` position note | Publisher / cadence-based ratio reveal |
| `redeem` circuit: prove winning position → private payout | Price-oracle resolution (R1, Chainlink/Pyth) |
| Public parimutuel YES/NO totals and odds, per market | Custom API feeds (R2, Switchboard) |
| Multisig/operator resolution (R5), disclosed | Optimistic oracle (R4) |
| Market lifecycle states + immutable resolution-spec hash | Sequencer batching + rotating relayers |
| Browser proving, MetaMask, existing `web/` extended | TEE hardening |
| Uniform gas limit across all three actions | |

### 3.1 One shared pool, many markets — decided day 1, not later

**Deposits go into a single shielded pool. Markets are distinguished by a `marketId` bound inside the position-note commitment, not by deploying a pool per market.**

This is a correctness decision about anonymity, not a convenience one:

| Design | Anonymity set |
|---|---|
| Separate pool per market | Only the depositors of *that* market. Ten markets with ten users each = anonymity set of 10. Weak enough to be worthless. |
| **Shared pool, `marketId` in the note** | **Every depositor across every market.** Same ten markets = anonymity set of 100, and it grows with total platform usage rather than per-market usage. |

Cost of doing it on day 1: one extra field in the Poseidon commitment, same as the outcome tag already needs. Cost of retrofitting it later: new note format, therefore new circuits, therefore migrating live positions. **This is the same "dependency sits in the middle, not at the boundary" trap that ruled out building on someone else's pool.** Decide once, on day 1.

Consequence to keep in mind: a note is spendable into *any* market, so `marketId` must be bound in the commitment hash exactly as strictly as the outcome tag — otherwise a position in a settled market is redeemable against a different market's pool.

Deferring the sequencer means **users must submit their own withdraw/redeem transactions**, which reintroduces the gas-link problem the POC README already warns about: an account that both deposits and redeems links itself in plain sight regardless of the proof. For the demo this is handled by instruction ("redeem from a second, unfunded-by-you account"), not by infrastructure. **This is the single largest honesty gap in the 4-day build and the UI must say so out loud**, exactly as the POC's UI already does.

## 4. What the site is allowed to claim

The current homepage says, under "Blind books":

> "Positions stay encrypted until settlement. Nobody copies your trade, because nobody can see it."

**The first sentence is not true of the 4-day build** and must change. Individual positions are hidden, but the aggregate is public and live, so a large enough bettor moves a number everyone can watch.

| Claim | 4-day build | Verdict |
|---|---|---|
| "Nobody knows which bet is yours" | true | **keep** |
| "No name on the ledger" | true | **keep** |
| "Redemption reveals nothing about your position" | true | **keep** |
| "Positions stay encrypted until settlement" | false — totals are live | **change** |
| "Private prediction market" | overclaim without C2 | **change** |
| "Odds are public" | true, and true in the 8-week plan too | **keep, state proudly** |

Suggested replacement for law 01, matching the original plan's own instruction to *"say the smaller thing plainly"*:

> **Blind books.** Nobody can tell which bet is yours, or what you staked. Odds are public; participation is not.

The user-visible loss from cutting C2 is exactly one thing, and it should be stated internally so nobody oversells it: **late money**. With live totals, a bettor arriving minutes before close reads the crowd's conclusion at lower risk than someone who bet early into fog. Encrypted pools with hourly ratio-only reveals are what fix this — that is why the original plan calls encryption *"not a privacy garnish; it is what makes the mechanism sound."* Every public prediction market shipping today has this same flaw, so this is parity with the field, not a regression below it — but it is the reason Phase 2 exists and it is not to be quietly dropped from the roadmap.

## 5. Resolution — the part that was not yet specified

### 5.1 The finding that shapes everything here

**[DOCUMENTED, `nisi-master-reference.md` §6, full 190-entry `monad-crypto/protocols` mainnet registry pulled]**

> **There is no UMA, no Reality.eth, and no Kleros on Monad.** Polymarket runs on UMA. Omen runs on Reality.eth plus Kleros. **You are building the resolver, not integrating one.**

This is the single most under-appreciated line in the reference document. Every competitor's resolution layer is a dependency they installed. Ours is a component we own, and it is *not* covered by any of the ZK work — a perfect shielded pool with a broken resolver is a broken product.

Live oracle providers on Monad: Chainlink, Pyth, Redstone, Stork, Supra, Switchboard, Band, Chronicle. eOracle is deployed but **dead — zero feed updates since 15 Jan 2026** [DOCUMENTED]; do not plan around it.

### 5.2 What the 4-day build ships: R5, disclosed

| Tier | What it is | Reference verdict | 4-day |
|---|---|---|---|
| R1 | Price / on-chain-metric oracles (Chainlink, Pyth) | **"SHIP ONLY THIS IN v1"** — zero human judgment, zero dispute surface | stretch goal, §5.4 |
| R2 | Custom API feed via Switchboard Feed Builder | PHASE 3 | out |
| R3 | zkTLS | **[UNVERIFIED]** whether a usable general verifier exists on Monad | out |
| R4 | Optimistic oracle, built by us | DEFER — *"the weakest link in the whole product"* | out |
| R5 | Multisig / committee resolver | **"ACCEPTABLE INTERIM"** for a v1 with disclosure | **ship this** |

R5 is not a fudge — the reference document explicitly blesses it for a v1 *provided the centralisation is disclosed*. The demo UI must say who can resolve, in plain words, on the market page. Not in a footnote.

### 5.3 Requirements that apply at every tier — these are day-1, not day-4

From `nisi-master-reference.md` §6, "Requirements regardless of tier". All four are cheap in contract terms and structural in consequence, so none of them are deferrable:

1. **Resolver address and a hash of the full resolution spec committed at market creation, immutable.** Spec text off-chain, hash on-chain. Without this the operator can silently redefine what "X happened" meant after seeing the pool. This is the cheapest single line of trust-minimisation in the product.
2. **A gap between betting close and resolution start.** Betting closes at `T`, resolution may not be submitted before `T + Δ`. The reference is blunt about why: *"last-second bets front-run known information, and unlike ordinary parimutuel bets that one **is** profitable."* Parimutuel kills ordinary MEV because payout is order-independent — this is the one front-running vector it does **not** kill, so it must be closed in the contract.
3. **Resolution stays fully separate from decryption.** Moot in the 4-day build (no committee to separate from), but the resolver must emit *only a branch selector* — never touch balances, never touch notes. Keeping that boundary now is what makes C2 droppable in later without redesign.
4. **"Closed, resolving, funds locked until X" is a first-class UI state.** The chain finalises in 600 ms; markets resolve in days. If the UI has only "open" and "settled", every market spends most of its life in an undefined state and users assume the thing is broken.

Market lifecycle to implement: `Open → Closed → Resolving → Resolved → Redeemable`. Five states, each visible in the UI, `Closed → Resolving` gated by requirement 2.

### 5.4 Pick market subjects that make R1 reachable

The resolver tier is decided by **what questions we seed**, not by resolver code:

- Seed **price / on-chain-metric markets** ("Will MON close above $X on date D", "Will protocol P's TVL exceed Y") and R1 becomes a genuine day-4 stretch goal: a Chainlink or Pyth read, no human in the loop, and the largest trust hole in the demo closes.
- Seed **fuzzy real-world markets** ("Will company C announce X") and we are locked into R5 multisig with no path to improve inside the window.

**Recommendation: seed price-resolvable markets for the demo.** Same product, same circuits, dramatically better trust story, and it is the only version of the resolver that the reference document endorses shipping.

## 6. Day-by-day

### Day 1 — `bet` circuit, market registry, shared pool
- New circuit: prove ownership of an unspent deposit note (merkle inclusion + nullifier, identical argument to `withdraw`), output **two** new commitments — remaining balance, and a position note.
- Position note commits to **`marketId` and outcome tag together**: `Poseidon(nullifier, secret, marketId, outcome)`. Both bound as strictly as each other — §3.1 and §7.
- Contract: market registry (`createMarket` storing `resolutionSpecHash`, `resolver`, `closeTime`, `resolveNotBefore` — all immutable after creation, §5.3 req 1 and 2), `bet()` accepting the proof, writing one nullifier, inserting two leaves, incrementing that market's public YES or NO counter.
- Fixed denomination throughout. See §7.

**Gate: bets land on testnet across two different markets from the same shared pool; double-bet with the same note reverts; a bet after `closeTime` reverts.**

### Day 2 — `redeem` circuit and resolution
- New circuit: prove ownership of a position note whose `(marketId, outcome)` matches the resolved market and winning outcome; payout to a recipient bound into the proof.
- Payout share is parimutuel: `stake × (total_pool / winning_pool)`, computed on public totals — no division inside the circuit.
- Contract: `resolve()` restricted to that market's registered resolver, reverting before `resolveNotBefore`, emitting loudly, writing **only a branch selector** (§5.3 req 3); `redeem()` verifying proof, blocking double-redeem by nullifier.
- Market lifecycle `Open → Closed → Resolving → Resolved → Redeemable` enforced in the contract (§5.3 req 4).
- **Redemption stays inside the shielded pool.** Non-negotiable, see §7.

**Gate: full cycle on testnet — deposit → bet → close → resolve → redeem — with redemption from a second account, nothing on-chain linking the two, and a resolve attempt before `resolveNotBefore` reverting.**

### Day 3 — Frontend and uniform gas
- Extend `web/` (deposit and withdraw already work) with bet, market list, per-market view, lifecycle state, redeem.
- Show live YES/NO totals and derived odds per market. Show anonymity-set size (total deposits in the shared tree, not per-market) honestly.
- Surface the resolver disclosure on every market page: who can resolve, and the resolution-spec hash. §5.2.
- Pad all three actions to one uniform declared gas limit. Not cosmetic — §1 measured that Monad bills the declared limit, and the limit is a public field, so differing limits fingerprint which action a user took.
- Carry the POC's existing gas-link warning into the betting UI, prominently.

**Gate: `deposit`, `bet`, `redeem` all declare an identical gas limit, asserted by a test.**

### Day 4 — End-to-end, real numbers, buffer
- Full cycle against Monad testnet, recorded gas for every action, published in the README the way the POC already does.
- Update site copy per §4 before anything is shown publicly.
- **Stretch, only if days 1–3 landed clean:** swap R5 for R1 on one price-resolvable market — a Chainlink or Pyth read behind the same `resolve()` interface (§5.4). Highest trust-per-hour available in this window. Do not start it if anything upstream is shaky.
- **This day is otherwise deliberately slack.** Constraint bugs and nullifier edge cases are where the time actually goes; scaffolding is not the risk.

## 7. Non-negotiables that survive the cut

Carried directly from the original plan. These are not optimisations.

| Rule | Because |
|---|---|
| **Redemption happens inside the ShieldedPool, never as a public claim** | A public payout retroactively deanonymises every position. Cutting this makes the privacy claim false, not weak. The original plan lists this as the one thing never cut. |
| **Fixed denomination, no arbitrary bet sizes** | With fixed sizes, a public counter leaks nothing about any individual. With arbitrary sizes, every counter movement is a per-user amount disclosure — which would make the public-totals cut far worse than it needs to be. |
| **All three actions padded to one uniform gas limit** | Monad bills the declared limit [MEASURED, §1] and the limit is public. Differing limits fingerprint the action. |
| **`marketId` and outcome tag both bound inside the commitment hash** | Outcome unbound → a losing note redeems as a winning one. `marketId` unbound → a note from a settled market redeems against a different market's pool. Equally fatal, one line apart. §3.1. |
| **Resolution-spec hash and resolver address immutable from market creation** | Otherwise the operator redefines what the question meant after seeing the pool. §5.3 req 1. |
| **Non-zero gap between betting close and resolution** | The one front-running vector parimutuel does not kill by itself. §5.3 req 2. |
| **Recipient bound into every proof** | Already done in the POC. Without it, proofs are stealable from the mempool. |
| **Never call `eth_estimateGas`** | You pay the declared limit regardless, and MetaMask inflates it wildly when estimation reverts. |
| **Say "shielded positions, public pool"** | Section 4. The claim must match the build. |

## 8. Honest risks in this window

1. **Trusted setup is a toy.** The POC's ceremony is one machine, one contributor — anyone who ran `setup.sh` can forge proofs. Fine for testnet and demo, **disqualifying for real value.** Must be stated wherever the demo is shown.
2. **No sequencer means users self-link.** Section 3. Mitigated by instruction only, which is weaker than infrastructure.
3. **R5 resolution is a trusted multisig.** Blessed as an interim by the reference doc, but only *with disclosure* — so the disclosure is mandatory, not optional. §5.2. The stretch goal in day 4 is the cheapest way to reduce this.
4. **We own the resolver, and nobody has checked it.** There is no UMA/Reality.eth/Kleros on Monad to fall back on [DOCUMENTED, §5.1]. Every hour spent on circuits is an hour not spent on the component that decides who actually gets paid. Weigh accordingly.
5. **Late money is unsolved.** §4. This is what Phase 2 exists to fix and the roadmap must keep it.
6. **The original plan's §9 risk is untouched by any of this.** Demand is still unvalidated. Four days of cryptography does not change whether anyone wants to bet on this. The cheapest derisking remains finding a small number of groups who will *commit* to running one market.

## 9. Relationship to the 8-week plan

Nothing here is throwaway. The commitment tree, nullifier scheme, note format, and circuit structure built in these 4 days are **exactly the ones Phase 2 extends** — the ElGamal accumulator hangs off the `bet` circuit by adding an `Enc(m)` output and a consistency constraint to a circuit that already exists.

That is also precisely why the third-party route was rejected: the accumulator has to read the value of the note being spent, which means the note format and the pool must be ours. A dependency at that position is not swappable later. This 4-day build is the first two-thirds of Phase 1, not a prototype to be thrown away.

The same reasoning is why §3.1 (shared pool, `marketId` in the note) and §5.3 (immutable spec hash, close/resolve gap, lifecycle states) are day-1 items despite looking like polish. All three sit *inside* the note format or the market record. Anything inside those is a rewrite later, not an addition.

**Resume point after day 4:** original plan Phase 1 remainder (sequencer, batching, R1 oracle resolution across all markets), then Phase 2 with the §2 correction factored into the estimate.
